# 架構與資料流

## 模組責任

1. Observer（觀察器）建立 ObservableState（玩家可觀察狀態）。
2. WorldModel（世界模型）只保留最新的可觀察快照。
3. Planner（規劃器）只接收該快照，回傳語意行動，不取得瀏覽器或原始狀態。
4. Executor（執行器）先經過共用輸入閘門；目前只修改本機模擬世界。
5. Observer（觀察器）重新產生新的觀察識別碼與快照。
6. Verifier（驗證器）比較前後狀態，確認語意行動的結果。
7. Logger（紀錄器）保存決策、原因、執行結果、驗證結果、錯誤與耗時。

瀏覽器本機測試頁是另一條隔離輸入驗收路徑，每輪透過 Playwright（瀏覽器自動化框架）送出點擊、選取及文字，之後讀取本機頁面上的結果。它不控制正式遊戲。

## 輸入與停止

所有模擬操作及本機測試頁的輸入，都經過同一 ActionGate（行動閘門）。狀態轉換與輸入派發共用同一把非同步鎖。

停止控制必須取得該鎖，故停止回應前，先前已進入派發區段的操作可能完成；停止回應之後再派發的操作均被拒絕。瀏覽器操作設定逾時，避免無限等待。停止狀態不可恢復，須重新啟動。

錯誤狀態也拒絕操作。普通模擬模式連續錯誤最多三次；有瀏覽器時第一次操作或監測錯誤即進入錯誤狀態並關閉專用瀏覽器。不做盲目重送；驗證失敗時最多按錯誤策略重新規劃。

## 鍵鼠隔離

- 啟動完整、有畫面的專用 Chromium（瀏覽器）。
- 使用專案內的獨立設定檔。
- 使用 Windows（作業系統）原生程序建立介面，指定獨立桌面物件。
- 不切換桌面，不要求遊戲進入使用者前景。
- 檢查隔離桌面上的視窗數，以及使用者桌面上的專用視窗數；後者必須為零。
- 只讀取前景程序識別碼與游標位置，不讀取其他視窗內容或鍵盤輸入。
- 專用程序群組在平台結束時清理瀏覽器子程序，避免背景殘留。
- 不呼叫全域鍵鼠注入、全域鍵盤鉤子或真實游標移動函式。

## 有畫面與背景渲染

普通最小化方案曾搶焦點，不列為可用啟動模式。最終方案把正常有畫面視窗置於獨立桌面，監控頁提供截圖。

啟動旗標停用背景計時器節流、遮蔽降速及渲染程序背景降速。這些旗標只是設定；是否持續更新仍由計時器、動畫幀與圖形錯誤量測確認，不能只因為旗標存在就判定成功。

## 日後導入 Rust（程式語言）

可觀察狀態與行動有版本編號，欄位可用 JSON（資料交換格式）序列化。規劃器邊界不帶瀏覽器物件、作業系統控制代碼或原始遊戲狀態。

後續可加入以程序標準輸入輸出或本機通道溝通的規劃器，實作相同輸入輸出契約，再逐步搬移模擬、搜尋及求解核心。目前沒有加入外部求解器、機器學習或完整遊戲規則。

## 第一版的模擬規則

模擬塔只有簡單兵力、鄰接、擁有者與升級；占領與增援立即完成，移動軍隊只保留一個模擬步長。這些規則供工程測試使用，不能拿來推定 Kiomet 的真實戰鬥結果。
