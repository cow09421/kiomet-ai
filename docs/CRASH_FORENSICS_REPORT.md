# 渲染崩潰鑑識（2026-09-27，五次同型）

## 結論

**已確定的直接故障：Chromium renderer（渲染程序）在 `chrome.dll` 固定指令處，對未配置保護頁做越界讀取。** 五份 Crashpad（崩潰傾印）一致：Windows 例外 `0xC0000005`（讀取存取違規）、`chrome.dll+0x710E1A7`、相同上層堆疊偏移。指令位元組 `8B 52 FF` 對應 `mov edx,[rdx-1]`；五次 `rdx-1` 都落在一個 64 KiB 保留且不可讀的區域起點。該區域前後各是已提交的唯讀頁。

**ROOT CAUSE CONFIDENCE（根因信心）：MEDIUM（中）**。對「同一渲染程序越界讀取路徑」的信心為 HIGH（高）；對更上層的觸發來源仍為 MEDIUM（中），因本機沒有該 `chrome.dll` 的符號檔，無法把固定位址還原成函式名稱。`Page.screenshot: Target crashed` 是平台在擷取時**察覺**渲染程序已崩潰，不能單憑錯誤字樣證明截圖造成崩潰。

## 時間線與排除

- 第四次崩潰前一分鐘，平台在 `RUNNING`，觀戰約 1 FPS（每秒畫面數），截圖耗時約 70–80 ms，沒有逐幀檔案佇列。當時未有研究偵錯器附著（Muse 交接敘述；無獨立全域會話計數），可降低「偵錯器單獨造成」的可能。
- 總程序樹記憶體：崩潰前 60 分鐘約 1324 MiB、45 分鐘 1477 MiB、30 分鐘 1543 MiB、15 分鐘 2012 MiB、5 分鐘 1643 MiB、最後一筆 1655 MiB。沒有崩潰前單調上升至峰值的型態；原有數據只記總量，尚不能完全排除單一程序局部資源問題。
- 例外類型是讀取存取違規，不是典型的 OOM（記憶體不足）終止或 WASM trap（網頁組件陷阱）。第四份傾印沒有 GPU 程序崩潰證據。
- 音訊注入、遊戲資料、截圖等是否作為上游觸發，**尚未證實**；不能宣稱已修復。
- 第五次在新程序、新對局開始約九分鐘後發生。崩潰前瀏覽器記錄到媒體解碼訊息，但不能證明它與崩潰有因果關係。遙測沒有顯示影格檔案佇列增長；最後一筆觀戰序號停止在 579。第五次當時有研究斷點工具；第四次沒有，所以斷點不是五次共同的必要條件。因觀察工具已遇到同型故障，本輪停止重複斷點實驗。
- 隔離啟動的三次失敗是**另一個故障**：GPU 子程序以 `0xC0000022`（存取被拒）退出，瀏覽器主程序再以 `GPU process isn't usable` 終止。改以一般主機權限啟動後，隔離桌面設定不變且瀏覽器成功執行。這些 `0x80000003` 傾印不可與上述渲染越界讀取合併計數。

## 最有價值的下一實驗

本輪已以 `tools/resource_telemetry.py` 每 20 秒取樣，原始資料在 `runtime/research/crash/resource-telemetry.jsonl`。下一個最有價值實驗是取得**此版本** `chrome.dll+0x710E1A7` 的符號或以相同隔離與遊戲情境對照另一個專用 Chromium 版本；同時比較有無媒體廣告載入。這些尚未完成，故上游根因及修復均標為 **未確認**。重啟後的對局、鏡頭、塔引用與座標必須重新建立。遙測工具中 `cdp_session_count`、`debugger_attached_count`、`artifact_queue_length` 欄位目前為 `null`（未能量測），不能將其當成零。
