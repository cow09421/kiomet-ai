# M2A canvas callback descriptor review

## Verdict

The static trace now proves the outer canvas listener adapter and the exact indirect-dispatch boundary, but the final registered callback remains dynamically selected. The captured mouse event enters generated wrapper function func1359 (table index 2504); that wrapper dispatches through another indirect call whose table index is loaded from the closure vtable at offset +20. The event-registration code obtains that vtable pointer from CanvasProps field +28 and does not initialize it. The pinned static artifacts reviewed here do not connect that field's writer to the app handler func1242 or to ClientBroker::mouse.

Therefore the callback-to-peek_mouse route and whether application handling is queued remain **UNKNOWN**. The synchronous part is limited to the browser callback entering the generated WASM wrapper and that wrapper's direct indirect-call instruction; a captured callback could enqueue an app message which runs later.

## App-handler candidate and queue boundary

The element segment maps func1242 to table index 438. Its disassembly (runtime/research/v2/func1242.txt) contains mouse-event logic: it compares the event name against mousedown at byte offset 0xdf605 and against mouseup at 0xe0155, reads the button at 0xe0176, and reaches KiometGame::peek_mouse calls including 0xe01a0 and 0xe0042. It is a plausible app/update-side handler, but no reviewed static store proves that the callback slot read by func539 ultimately selects index 438.

The callback wrapper's call-indirect is direct and synchronous within the current JavaScript event callback. That fact does not settle what the captured function does next. The app-side mouse processing in func1242 is reached through a separate table entry and has no statically proven caller edge from the callback slot above. Consequently these artifacts do not establish same-stack completion, Yew scheduling, a microtask boundary, or a later task before route reading.

## Queue and scheduling boundary

For a caller that reaches func2181, the queue write is concrete: func2181 copies a 248-byte message into the queue and increments its length (WAT lines 489286–489305; binary offsets 0x10e4da–0x10e503). Only when the old length is zero does it call func4173 with the supplied callback/task pair (lines 489306–489310; 0x10e506–0x10e50d). func4173 does not call func1242 inline. It retains the task data, appends a scheduler item through func3327 → func6830 → func3547, and calls func1419 (WAT 582319–582343; 0x14031a–0x14034e). The scheduler item uses the static callback record at 1108800; its word at +12 is table index 910, which maps through the element segment to func1921. func1921 polls an inner future through its own indirect call at WAT lines 472329–472334 (0x105ecf–0x105edc), rather than directly calling func1242. The reviewed static trace does not resolve that inner poll target to func1242.

func1419 is a conditional one-time start: it enters setup only while byte 1367968 is zero, sets that byte to one, then calls func1388 and func1645 (WAT lines 420860–420866 and 420955–420957; 0xec1f2–0xec204 and 0xec2cf–0xec2d4). Thus later empty-queue edges still append scheduler work, but func1419 itself returns after the startup guard is set. In the startup path, func1388 can synchronously invoke a saved callback only if state byte 1366884 equals 2 and slot 1366888 is nonzero; it clears that slot before the indirect call (WAT lines 416846–416864; 0xea272–0xea29f). If the state is still 2 afterward, it saves the callback state and enters func4390 (lines 416885–416922; 0xea2d3–0xea335). This is a deferred/reentrant Promise-state path, but the static trace does not identify its saved callback as the newly appended 248-byte app message.

func1645 queues the executor continuation and coalesces duplicate scheduling with a byte flag at callback-state offset 28. If that flag was already set, it does not schedule another host callback. When the flag was clear, byte 1366884 selects the host mechanism: value zero calls Promise.then (WAT lines 447880–447889; 0xf99f2–0xf9a10), while a nonzero value calls queueMicrotask (lines 447892–447894; 0xf9a16–0xf9a1e). The generated JavaScript shims call `getObject(promise).then(getObject(callback))` and `queueMicrotask(getObject(callback))`, respectively; both defer the continuation to the JavaScript microtask queue. These are conditional wake paths in func1645, which func1419 reaches only on its first start. On later func4173 calls, the one-time guard makes func1419 return, so this trace does not prove that each newly appended task causes a fresh Promise/microtask wake. It proves task enqueueing and a conditional startup wake, but not when func1921 drains that task or whether the inner future poll reaches func1242. Nor does it establish that the registered canvas callback takes this path until the CanvasProps vtable at field +28 is identified.

## Precise unresolved writer

The final unresolved producer is the writer of the CanvasProps closure vtable pointer at `var3+28`; `var3+24` supplies the captured data pointer. func4036 copies the pair into the listener closure. func1359 then obtains the indirect-call table index from `load(vtable+20)`. The static queue trace proves that an empty queue causes a task enqueue and reaches func1419's conditional one-time startup path if the callback reaches func2181. It does not prove a fresh microtask wake for every task, when the queued task is drained, or that the canvas mouseup callback selects a vtable method that calls func2181 or func1242. Resolving the field writer and its vtable method is still necessary to bind canvas mouseup to the app's peek_mouse route. No runtime memory inspection or actor-state read was used to fill this gap.

Until that writer and scheduling boundary are resolved, keep the broad listener checks, classify callback route continuity as **UNKNOWN**, and do not grant formal command or transition credit from the canvas event receipt alone.
