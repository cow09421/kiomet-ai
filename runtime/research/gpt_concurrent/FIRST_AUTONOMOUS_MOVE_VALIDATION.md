# 第一次可稽核自主調兵驗證方案

這是交給 Muse 的**實作與驗收步驟**，本輪不執行任何遊戲操作。只有當使用者在當次流程中已明確授權、平台已具備安全閘門與稽核欄位時，才由 Muse 執行；本文件本身不是解除閘門的授權。

## 執行前：全部必須 PASS（通過）

1. 確認平台與真實控制器各有唯一程序 PID（程序編號）、啟動時間、controller_epoch（控制器世代）和每數秒更新的心跳；`--live` 真正將控制器接入常駐生命週期。若只是 `app.py` 的心跳真實分支，**FAIL（失敗）**。
2. 儀表板的 Planner／Executor／Verifier（規劃器／執行器／驗證器）狀態來自**新鮮心跳及實際元件**；不得用舊 `first_move_candidate.json` 的 `DRY / LOCKED`（乾跑／鎖定）冒充新提案。明確確認真實授權、閘門 RUNNING（執行中）、目前對局識別與未決行動數為零。
3. 先以自然移動部隊資料驗證第三輪的 24 位元組項目、塔 `+0/+12` 兩集合、兵力 `+14..+20` 及畫面座標容差；如果尚無至少三組成對真值，首次自主行動的驗證結果須維持 UNKNOWN（未知），不能因送出就宣稱成功。
4. Fresh Observe（新鮮觀察）：同一對局與節拍世代，逐塔檢查參照位址、48 位元組範圍、兵力標記、塔型、擁有權、集合與路徑完整性；讀到不合法 `UnitsEither`（兵力聯合型態）標記時重新錨定，絕不送操作。
5. Fresh Proposal（新鮮提案）與 Fresh Preflight（新鮮預檢）：來源為我方、目標合法、路徑和螢幕座標來自同一相機與觀察世代、可派兵力可信、對局未切換、沒有另一個未決 action_id（行動識別）；在派送前重新核對一次。
6. 先持久寫入 `action_id`、發起者 `AUTONOMOUS_CONTROLLER`（自主控制器）、控制器與平台 PID、對局、來源／目標塔、路徑、期望兵力、畫面座標、授權來源、事前來源／目標塔及兩側集合快照，再允許一次 POST（網頁請求）。

## 單次派送與驗證

1. 控制器只送**一個** `/api/execute-move`（調兵請求），請求與平台日誌使用同一 `action_id`。記錄瀏覽器定向拖曳結果、按下／放開時間與事前／一秒後畫面。平台回 `ACTION_SENT`（輸入已送出）時僅標 DISPATCHED（已派送）。
2. 送後連續取得當局唯讀快照；保留每次觀察時間、來源兵力、來源出站部隊、目的入站部隊、每個候選路徑／擁有者／兵力／進度、目的塔擁有權，以及畫面上的部隊中心。以本輪匹配配方去重並關聯本次 `action_id`。
3. 只有符合 `GPT_REAL_VERIFIER_SPEC.md` 的強證據組合才將 `verified_moves` 加一；目的塔變我方且與這支部隊到達相關時才將 `verified_expansions` 加一。若未觀察到、候選多義、對局切換或超時，記 UNKNOWN／AMBIGUOUS（未知／多義）及原因，不得自動重送。
4. 結束本次驗證後清除舊提案，**重新觀察**並產生新版本，才容許下一個操作。連續三個不明或未驗證結果進 FAILSAFE（安全封鎖）。

## 驗收輸出

產出單筆不可覆寫的 action journal（行動日誌）：`action_id`、發起者、兩個 PID、對局、派送時間與結果、before/after（事前／事後）狀態、出站與入站匹配部隊鍵、來源兵力差、目標擁有者變化、證據檔路徑、最終 `VERIFIED_MOVE`／`VERIFIED_EXPANSION`／`UNKNOWN`、原因與下一個狀態。儀表板分開顯示「已派送」、「已驗證移動」、「已驗證擴張」三個累計與最近一筆來源。若只有 `sent_actions` 增加而無上述紀錄，驗收 **FAIL**，不能再稱為自主成功。
