# 2031 被動擷取方案（供 Muse 後續評估）

## 判定

**原始 7 位元組輸出的安全長壽命擷取點：NOT FOUND（未找到）。** 8 個呼叫位置都把結果寫在呼叫者的堆疊等效暫存區。拖曳預覽及釋放路徑會消費它，卻不把原始 `Units`（兵種數量結構）存入 `Drag`（拖曳狀態）或 `Command`（命令）。單純在影格之間輪詢那些位址，會讀到已重用的暫存記憶體，不能算直接驗證。

## 候選 A：自然部署後的 `Force`（移動兵力）

| 欄位 | 靜態結果 |
|---|---|
| 觸發條件 | 遊戲**自然發生**的部署事件；不由本研究送出命令 |
| 正式版函式 | 1791 `Tower::deploy_force`，2031 呼叫在 `0x10041C`，1963 `Tower::send_force` 在 `0x1004BA` 被呼叫 |
| 位址推導 | 1791 的 `local3` 是當次函式框架基底；原始結果在 `local3+17..23`；複製後位於 `Force`（移動兵力）起點 `local3+24` 的 `+14..20`。這些是**相對位址**，不是跨影格固定線性記憶體位址 |
| 輸出生命週期 | 原始 7 位元組到 1791 返回為止；事件副本隨事件傳遞；事件套用後的 `Force`（移動兵力）由塔的入站／出站兵力集合持有，直到遊戲邏輯移除 |
| 讀取時間窗 | 只能在事件已自然產生且尚未被移除期間，透過**既有**只讀觀察途徑讀取狀態；不嘗試掃描已釋放的堆疊緩衝區 |
| 預期結構 | 原始 7 位元組 `Units`（兵種數量結構）；先讀 tag（型別標記）再依現有解碼器處理 `Many`（多兵種）或 `Single`（單兵種），不得把 `Single` 的非作用中位元組解成多兵種 |
| 塔關聯 | 從事件／`Force`（移動兵力）的路徑起點及來源塔編號關聯；不要只靠畫面位置推測 |
| 風險 | MEDIUM（中）：自然事件可能不發生，且持久狀態並非原始 2031 函式返回當下的獨立觀測；同一塔可能同時有多個兵力 |
| 需要中斷點 | NO（否），前提是 Muse 已有可讀的事件或兵力狀態通道；本輪未驗證該通道是否存在 |

**限制**：候選 A 可驗證部署結果與 2031 離線鏡像是否一致，但不能在沒有自然部署時取得直接輸出。也不能藉此宣稱拖曳預覽的輸出被持久保存。

## 候選 B：既有塔狀態的離線重算

如果現有 Observer（觀察器）已提供來源塔的 `tower_ref+38` 單位資料、`tower_ref+46` 塔型與必要 tag（型別標記），可在研究程序之外以已通過的離線鏡像重算 `force_units`（可派兵單位）。這是 **derived（推算）**，不能計作正式執行期直接輸出核驗，也不應增加 `Runtime`（執行期）呼叫。優點是完全不需要拖曳、派兵、掛鉤或中斷點。對 `Single`（單兵種）仍保持目前的 UNKNOWN / PARTIAL（未知／部分成立）狀態。

## 不建議的擷取方式

- `0x057E3B`、`0x0D9D70` 返回後暫存緩衝區：有效時間只在對應函式框架內；一般輪詢容易錯過或讀到重用資料。
- 直接呼叫 2031：會繞過自然觸發條件，也違反本輪隔離要求。
- 長時間偵錯中斷點、附加偵錯器、CDP（Chrome 開發者工具協定）密集暫停：目前沒有必要，且無法視為低風險被動觀察。
- 由 GPT 觸發拖曳或派兵以造樣本：本輪禁止；Muse 的真實執行期工作不受此研究干擾。

## Muse 的唯一後續驗證步驟

等 Muse 自身流程**自然**觀察到一次部署時，若已有只讀兵力事件或塔狀態通道，就在同一筆資料中記錄來源塔、事件路徑、事件內 7 位元組 `Units`（兵種數量結構）或逐兵種數量，並與部署前塔資料和離線鏡像對照。若沒有現成通道，維持 `DIRECT OUTPUT 0/5`（直接輸出零個有效樣本），不要為這項驗證單獨新增會暫停或操控遊戲的裝置。

本檔是未執行的靜態方案；**沒有**附加程式、讀取執行期記憶體或送出遊戲行動。
