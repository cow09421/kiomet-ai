# 真實調兵驗證器規格

現有 `src/kiomet_ai/proposal.py:197-220` 的 `verify_post_action`（行動後驗證）用合成／歷史狀態判斷：目標任何變化即可 `TARGET_CONTESTED`（目標受影響），來源任何變化即可 `SOURCE_CHANGED`（來源變化）；`tools/live_controller.py:264` 目前把 `force_observed`（觀察到部隊）固定設為 `False`（否），且只在送出八秒後取一次快照。這些條件不足以證明一次真實操作造成移動，特別是補給線、其他玩家操作、自然生兵／耗兵、戰鬥或切局都能造成類似變化。

## 行動識別與先備快照

每次提案產生不可重用的 `action_id`（行動識別碼），持久記錄 controller_epoch（控制器世代）、發起者、平台 PID（程序編號）、對局、來源塔、目的塔、期望完整路徑、期望兵力組成或範圍、當局 owner（擁有者）、畫面座標、發送時間、發送前的塔與兩側部隊快照、觀察版本。平台接受 POST（網頁請求）時回寫相同識別；`sent=True` 只代表拖曳按下／放開成功，稱 DISPATCHED（已派送），不得稱 VERIFIED_MOVE（已驗證移動）。若請求逾時，先查同一 `action_id`，不能重新派送。

## 證據階級

| 證據 | 階級 | 原因與使用限制 |
|---|---|---|
| A. 來源兵力下降 | WEAK（弱） | 補給線、戰鬥、另一個操作、其他遊戲規則也會造成；單獨無效 |
| B. 來源 `outbound`（出站）集合出現新部隊 | MEDIUM（中） | 若無相同來源、路徑、擁有者及時間匹配，可能是他人／自動續行；需與事前基線比差異 |
| C. 目標 `inbound`（入站）集合出現新部隊 | MEDIUM | 同上；它是來源出站鏡像的另一持久表示 |
| D. 新部隊的路徑、兵力、擁有者、進度與本次 action_id 範圍吻合，且跨兩個快照沿路前進 | STRONG（強） | 主證據；兩側鏡像互證最佳。若兵力組成未知，需更嚴格時間窗與唯一性 |
| E. 目標擁有者變為我方 | MEDIUM（單獨）／STRONG（接在 D 之後） | 同盟、其他部隊、自然事件也可改變；只有與本次移動鏈相接才證明擴張 |
| F. 用戶端介面回應、動畫或一秒後截圖 | WEAK | 能表明輸入／畫面反應，不能單獨證明權威遊戲命令已被接受 |
| G. 伺服器／世界狀態中與本次來源、路徑、兵力匹配的更新 | STRONG | 若可唯讀取得，優先於畫面；仍需對局、時間與唯一性匹配 |
| 單純 `ACTION_SENT`、舊檔案、跨局指標、沒有新鮮度的顏色 | INVALID（無效） | 不能作遊戲世界成功證據 |

## 最低判準與避免假陽性

`VERIFIED_MOVE`（已驗證移動）需先有平台 `sent=True`，再有**同局、同一觀察世代**的事前基線與新出現的匹配部隊。接受兩種組合：① B+C+D，兩側鏡像與路徑／兵力相符；② B 或 C + D + G，單側部隊與權威世界更新相符。若路徑／兵力無法觀察，單靠 A+E 或 A+F 仍是 UNKNOWN（未知）。若畫面中有兩支同路同色同兵力且時間接近的候選，必須保持 AMBIGUOUS（多義），不得任選一支。A 是輔助一致性檢查；自然下降不能使證據升級。

`VERIFIED_EXPANSION`（已驗證擴張）除上述移動證據，還需同一路徑的部隊抵達後，目的塔 owner（擁有者）在權威狀態中變為我方，且無其他同時候選可解釋。若只是目標改色、未追到本次部隊，只能標「目標變化，歸因未知」。若部隊送出但戰死，仍可保留 `VERIFIED_MOVE`，不能標擴張。

## 時間窗與失敗規則

事前應在派送前一個節拍內取得快照；送出後盡早連續觀察，至少覆蓋兩個遊戲節拍（來源碼每秒四節拍），直到新部隊被匹配或超過按路徑估計的單段時間加寬限。輪詢節奏需依既有唯讀通道成本量測，避免附加侵入式偵錯器。八秒後**單次**快照可能錯過已到達、戰死或重新分配的 24 位元組項目，不可當唯一驗證。

切局、控制器世代改變、來源塔指標換代、記憶體快照不完整、owner（擁有者）不明、路徑不符或有多個候選時，回傳 UNKNOWN／AMBIGUOUS；連續三次未驗證進 FAILSAFE（安全封鎖）。保存可稽核的 before/after（事前／事後）摘要、部隊鍵、證據時戳與拒絕原因，避免只存一個布林值。
