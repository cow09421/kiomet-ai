# 升級數量回呼根來源：第三輪靜態追查

本輪在移動部隊 P0（優先工作）完成後才開始此 P1（次優先工作）。仍只檢查已下載的正式版 WebAssembly（網頁組合語言）及前輪證據，沒有連接目前執行期。

## 已追到的路徑

1. 正式版元素表的 `elem[438]` 指向函式 `1242`；其型別是 `(i32)->i32`（接收一個 32 位元參數、回傳一個 32 位元數值），而直接呼叫者清單為空。這支持 `1242` 透過間接回呼執行。證據：`runtime/research/source-map/production-details.txt` 的元素表與 `production-functions.json`。
2. `1242` 的第一參數就是前輪命名的 callback root（回呼根）；其 `+592..+645` 是 27 個 `u16`（16 位元無號整數）的玩家塔型數量。`1242/0x0D5493` 把同根指標放入閉包；`3492` 從閉包 `+4` 取回，再把 `root+592` 傳給 `2425 TowerType::has_prerequisites`（檢查升級前置條件）。前輪已交叉驗證介面複製的 54 位元組數量陣列。
3. `1242` 的開頭另從 `root+49016` 讀取物件指標（`0x0CC7E4..0x0CC7ED`），說明此參數是大型用戶端狀態基址，不是 54 位元組數量陣列的獨立指標。

## 未解的第一哩

元素表只告訴我們**哪個函式**可由回呼表呼叫，並不存放某一局的實際 `root` 位址。正式版 `1242` 沒有直接呼叫者，因此單靠呼叫圖無法推得第一次傳入的物件位址。現有塔錨點是 `tower_ref`（塔位址）；尚未找到從它回溯到 `root` 的安全、穩定指標鏈。不能從 `root+49016` 的讀法反向猜出根，亦不能跨局快取某次根位址。

**Callback Root Provenance（回呼根來源）: PARTIAL（部分完成）**：回呼表 `438→1242`、入口第一參數及閉包轉交鏈已確定；提供該入口參數的上層回呼物件／JavaScript（網頁腳本）綁定仍未知。

**Stable Observer Path（穩定觀察器路徑）: UNKNOWN（未知）**。目前沒有足夠靜態證據交付 `tower_ref→root` 或固定全域位址配方。

Muse 日後若**既有**唯讀通道已能取得當局回呼根，才可在同一觀察世代讀 `root+592` 起的 54 位元組，按 27 個小端序 `u16` 解碼，並與自然顯示的官方升級進度核對。若拿不到根，繼續保留未知；不得為此新增偵錯器、遊戲動作或跨局位址快取。
