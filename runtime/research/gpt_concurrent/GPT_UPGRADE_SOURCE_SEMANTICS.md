# 升級狀態：公開原始碼語意

## 權威輸入

`Tower`（塔）在 `vendor/kiomet-ref/common/src/tower.rs:49-59` 保存 `player_id`（擁有者）、`tower_type`（塔型）及 `delay: Option<NonZeroU8>`（可為空的非零 8 位元延遲）。玩家塔數量不是每座塔內的兵力：`NonActor.tower_counts`（非演員更新中的塔型數量）在 `common/src/protocol.rs:43-55` 定義為固定長度 `TowerArray<u16>`（以塔型索引、每格 16 位元的陣列）。原始碼註解明言數量封頂於 `u16::MAX`，**不計正在升級的塔**。`TowerState::apply`（塔狀態套用更新，`client/src/state.rs:35-57`）每次伺服器更新都替換 `non_actor`（非演員資料），因此數量屬於伺服器送來、由用戶端保存的更新狀態；用戶端不必每次掃描畫面上的塔。

## `tower_ref+47` 的精確語意

- **型別**：`Option<NonZeroU8>`（可為空的非零 8 位元整數）。正式版記憶體表示為 1 位元組：`0` 對應 `None`（沒有延遲），`1..255` 對應剩餘 tick（更新節拍）。
- **單位**：1 tick（更新節拍）= 0.25 秒。`common/src/ticks.rs:4` 使用 `GenTicks<4>`（每秒 4 節拍）；共用 `GenTicks` 定義的 `PERIOD_SECS`（每節拍秒數）為 `1 / FREQUENCY_HZ`。
- **用途**：塔的**通用暫停倒數**。`Tower::active`（塔是否可用，`common/src/tower.rs:84-87`）要求沒有延遲。`common/src/chunk.rs:159-167` 的每次區塊更新，在有延遲時減 1，並跳過當次塔的兵種生成／衰減；為 0 時恢復正常生成。它包含升級建造時間，也可承載電磁脈衝的暫停效果，不能單獨視為「尚未送出的升級命令」。
- **寫入**：升級輸入套用時，`common/src/chunk/event.rs:196-210` 先改塔型，再把新塔型的 `TowerType::delay()`（塔型所需延遲）轉為非零 `u8` 寫入。`common/src/chunk.rs:332-344` 遭電磁脈衝時，把延遲設為目前值與脈衝延遲的較大者；`Unit::EMP_SECONDS`（電磁脈衝秒數）換算後為 240 tick（60 秒）。塔失去擁有者且被降至基礎塔時，`common/src/chunk.rs:394-403` 清為 `None`（無延遲）。新塔建構也以 `None` 初始化（`common/src/tower.rs:67-79`）。
- **最大來源**：正式版 `TowerType::delay`（塔型延遲）查 27 個 16 位元表值，靜態表最大為 160 tick（40 秒）；電磁脈衝可設到 240 tick（60 秒）。儲存型別本身上限 255；目前已確認的正式版寫入規則最大 240。不能把 255 當成遊戲實際會使用的時間。

## 升級候選與按鈕

`TowerType`（塔型）是 `repr(u8)`（1 位元組列舉，`common/src/tower.rs:226`）。`can_upgrade_to`（是否直升目標，`:365-367`）要求 `target.downgrade() == Some(current)`（目標的降級來源等於目前塔型）；`upgrades()`（直升目標集合，`:369-370`）據此產生候選。塔的基礎型也會額外顯示為降級候選（`client/src/ui/tower_overlay.rs:178-180`）。

每個候選目標的 `has_prerequisites`（已滿足前置條件，`common/src/tower.rs:437-440`）對固定陣列每種塔型比較 `count >= target.prerequisite(type)`。進度文字如 `Factory 0/2`（工廠 0/2）代表目前玩家持有 0 座工廠、該目標需要 2 座，與單座塔的 `Units`（兵種數量）無關。

官方用戶端升級按鈕的資料需求與分層如下：

1. **塔本身**：目前塔型、擁有者是否為自己、剩餘延遲是否為 0（`tower_overlay.rs:136-181`）。非己方或仍在暫停的塔不顯示升級候選。
2. **玩家狀態**：`tower_counts`（各塔型持有數）及來源定義的需求數量。未滿足需求時按鈕停用（`:182-188`）。
3. **用戶端解鎖狀態**：等級低於 Rank 3（第三級）、獎勵廣告可用、目標層級大於 0、且尚未解鎖時，按鈕顯示鎖並導向解鎖視窗；這與前置條件是否滿足分開（`:110-128,182-188`）。
4. **伺服器權威性**：用戶端點擊後送 `Command::Upgrade {tower_id,tower_type}`（升級命令，`client/src/game.rs:710-724`）。正式版命令驗證另檢查來源塔存在、擁有權、延遲、目標塔型與前置條件。用戶端當下可按不保證伺服器會接受過期狀態。

`Ruler`（國王）旗標與塔內兵力容量不是升級候選的直接條件。容量會在升級**套用後**由 `Tower::reconcile_units`（調整單位容量）處理。排名／解鎖會影響按鈕導向，不改變 `has_prerequisites`（前置條件比較）。

## 模型失效條件

`tower_counts`（塔型數量）隨每次伺服器更新而替換；玩家身份、對局或頁面重新建立時必須重新取得目前的狀態根指標及自我身份。不能沿用上一局的裸記憶體位址或數量。若只有塔型、延遲、擁有權與數量，可算候選及前置進度；若要完全重現「點擊後是否直接送升級命令」，還要等級、解鎖集合與獎勵廣告可用性。
